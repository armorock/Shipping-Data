# Jacks_Data_Improvement_Plans

**Author:** John Leitzke  
**Last updated:** 2026-05-26  
**Purpose:** Multi-source, source-traceable job code database with conflict detection and plant audit

---

## What This Is

A standalone data pipeline that merges job metadata from six sources into a single JSON database. Nothing here touches `01_build_job_code_registry.py`, `02_jobcode_repair.py`, or the `Job Codes/` markdown files — it reads from those as inputs but never writes to them.

**Outputs:**

| File | Description |
|---|---|
| `output/jobcode_db.json` | One record per job code, every field tagged with its source, conflicts stored inline |
| `output/plant_conflict_report.xlsx` | All job codes where plant data doesn't fully agree across sources |
| `output/problem_children.xlsx` | Short list requiring manual review (genuine plant conflicts) |

## Data Sources

Six sources are merged per job code. When sources conflict, the highest-confidence source wins unless a CONSENSUS_OVERRIDE fires (see Conflict Resolution below).

| Source | Confidence | What It Provides | File |
|---|---|---|---|
| **BOM** (Bill of Material) | Tier 0 — highest | project name, city, state, zip, contractor, release date | `MASTER CSV FILES/all_bom_union.xlsx` |
| **Dispatch Board** | Tier 1 | city, state, plant | `MASTER CSV FILES/Dispatch_Board_Master_2019-2025.csv` |
| **NetSuite** | Tier 1 | customer, shipping city/state/zip, job value, fulfilled status, order date | `data/netsuite_jobs.csv` (generated by `convert_data.py`) |
| **Shipping (BABY)** | Tier 2 | customer, city, state, zip, county, plant | `MASTER CSV FILES/All Shipping Data BABY.xlsm` |
| **Notion** | Tier 2 | city, state, county, bidding contractors, job status | `data/notion_export.csv` (generated by `convert_data.py`) |
| **Markdown** | Tier 3 | plant, customer, city, state, zip, year | `Job Codes/*.md` |

## convert_data.py

Converts the raw Notion ZIP and NetSuite XLS exports into clean CSVs that `jl_build_jobcode_db.py` can read.

**Notion output** (`data/notion_export.csv`):

| Column | Description |
|---|---|
| Job Code | Normalized 3-letter code |
| City | Project city |
| State | 2-letter state abbreviation |
| County | County name |
| Bidding Contractors | Comma-separated list |
| Job Status | Active / Won / Lost / etc. |

**NetSuite output** (`data/netsuite_jobs.csv`):

| Column | Description |
|---|---|
| Job Code | Normalized 3-letter code |
| Customer | Contractor/customer company name |
| NetSuite Date | Earliest order date (YYYY-MM-DD) |
| Fulfilled | True/False — True if any line item was fulfilled |
| Shipping City | Ship-to city from ERP |
| Shipping State | Ship-to state (2-letter) |
| Shipping Zip | 5-digit zip |
| Job Value | Sum of all line item amounts (excludes AvaTax/subtotal rows) |

Re-run `convert_data.py` whenever new exports are dropped in `data/`.

## jobcode_db.json — Field Reference

One flat object per job code. Every data field has a companion `_source` tag. When sources disagree, a `_conflict` field explains the disagreement and a `_resolution` field records how it was handled.

**Identity**

| Field | Description |
|---|---|
| `job_code` | 3-character primary key |
| `project_name` | Job name from BOM or Dispatch |
| `project_name_source` | `BOM` or `Dispatch` |

**Location** (city/state/zip resolved across all six sources)

| Field | Description |
|---|---|
| `shipping_city` | Best-available ship-to city |
| `shipping_city_source` | Which source provided the value |
| `shipping_city_resolution` | `MATCH` / `CONFLICT` / `SINGLE_SOURCE` / `CONSENSUS_OVERRIDE` |
| `shipping_city_conflict` | Human-readable description of disagreement |
| `shipping_state` | 2-letter state |
| `shipping_zip` | 5-digit zip |
| `shipping_county` | County (Shipping primary, Notion fallback) |
| `shipping_county_source` | `Shipping` or `Notion` |

**Customer / Contractor**

| Field | Description |
|---|---|
| `customer` | Invoice customer resolved from NetSuite → Shipping → Markdown |
| `customer_source` | Which source provided it |
| `customer_resolution` | Conflict resolution outcome |
| `contractor` | Contractor from BOM release document |

**Plant**

| Field | Description |
|---|---|
| `plant` | `BC` / `SS` / `PC` / `BC/SS` / `SS/PC` |
| `plant_source` | Which source(s) determined this |
| `plant_alec` | What the markdown file records |
| `plant_resolution` | `MATCH` / `CONFLICT` / `SINGLE_SOURCE` / `MULTI_PLANT` / `NO_DATA` |
| `plant_conflict` | Conflict detail string |

**NetSuite Informational** (not conflict-resolved, appended as-is)

| Field | Description |
|---|---|
| `in_netsuite` | True if job code appears in NetSuite export |
| `netsuite_date` | Earliest order date from NetSuite |
| `netsuite_fulfilled` | True if any line item was fulfilled/shipped |
| `netsuite_job_value` | Total job value from NetSuite line items |

**Notion Informational**

| Field | Description |
|---|---|
| `in_notion` | True if job code appears in Notion export |
| `bidding_contractors_notion` | List of bidding contractors from Notion |

**Presence Flags**

| Field | Description |
|---|---|
| `in_bom` | True if job appears in BOM union |
| `in_dispatch` | True if job appears in Dispatch Board |
| `in_shipping` | True if job appears in Shipping BABY |
| `in_markdown` | True if a markdown file exists for this job |

**Release Info**

| Field | Description |
|---|---|
| `year_released` | Year from BOM or markdown |
| `date_released` | Full release date from BOM |

## Conflict Resolution Logic

| Resolution | Meaning |
|---|---|
| `MATCH` | All sources agree |
| `SINGLE_SOURCE` | Only one source has data — no conflict possible |
| `CONFLICT` | Sources disagree; highest-confidence value used; flagged for review |
| `CONSENSUS_OVERRIDE` | BOM says X, but Dispatch + Shipping + Markdown all independently say Y — override BOM with Y; flagged for review |
| `MULTI_PLANT` | Shipping records confirm the job split across two plants (see below) |

**Confidence order:** BOM (0) > Dispatch = NetSuite (1) > Shipping = Notion (2) > Markdown (3)

---

## Plant Assignment and Multi-Plant Logic

Manufacturing plant is determined from Dispatch Board, Shipping BABY, and Markdown. BOM does not carry plant data.

**MULTI_PLANT** fires when Shipping records (across all rows for a job code) show activity at two plants in a known valid split combination. This is expected — Armorock regularly ships large structures (84", 96", 120", 144", 192" diameter) from Sulphur Springs while smaller structures go to Boulder City or Plant City.

Valid split combinations:
- `BC/SS` — Boulder City + Sulphur Springs (geographic or size split)
- `SS/PC` — Sulphur Springs + Plant City (large structures from SS until PC acquired that capability)

A job code with `plant_resolution = MULTI_PLANT` is resolved correctly — it does not appear in `problem_children.xlsx`.

## How to Use the JSON in Excel (Power Query)

1. Open Excel → **Data** tab → **Get Data** → **From File** → **From JSON**
2. Point it at `Jacks_Data_Improvement_Plans/output/jobcode_db.json`
3. Click **To Table** → **OK** → expand columns you want → **Close & Load**
4. Build any pivot table from there
5. Refresh: **Data → Refresh All** after re-running the pipeline
